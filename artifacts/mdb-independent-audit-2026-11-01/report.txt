Fresh independent MDB parser audit
1 November 2026

Bella is the best starting point among the implementations tested, but it is not universally superior or complete. Its current native-corpus catalogue is accurate, its direct project selection is better than current OldScanner, and its performance is substantially better. One real classification omission affects 30 native JPEG/JPED files. Older code also exposes useful recorded fields that Bella discards. Keep Bella's core and make targeted improvements; the evidence does not support reverting to an older parser or treating MDVx as a correctness oracle.

Scope and method

The reviewed checkout is 20220f2b4c2b7ff6ef3d017a77568e5edf7de7cd. Existing project documentation, earlier review evidence and fixtures were excluded. All findings below come from current executable/source code, source extracted from Git, newly inventoried native databases, newly retrieved external publications, and newly generated test outputs. Application source was not changed.

A fresh filesystem walk and supplemental system-volume walk visited 577,305 directories and found 411 .mdb paths. Of these, 398 were excluded as existing fixtures, existing evidence, or temporary/prior-generated material. The 13 remaining readable inputs comprise seven distinct Avid Bento databases and six unrelated LMDB files. All 13 were run through the current Bella parser, current OldScanner, and original MDVx MDB code in isolated processes. Original input SHA256 hashes were unchanged. There were 449 traversal access errors; four on EDIT were its protected .Trashes, .Spotlight-V100, .TemporaryItems and .DocumentRevisions-V100 directories. This is coverage of readable original files, not a claim about inaccessible locations. The supplemental walk pruned duplicate Data-volume paths only when device and inode proved they alias already searched root paths; it found no additional MDBs.

Accuracy of current implementations

Bella and current OldScanner return exactly the same file and master identities and direct master relationships. Their common semantic values agree for descriptor lengths, sample rates, audio display clocks, all 1,513 audio frequencies, all 2,515 semantic bit depths, raster dimensions, explicitly recorded coding labels, master names, bins, types and precompute categories. All 232 comparisons where Bella establishes recorded drop-frame state also agree. Optional-detail mode changes only the intended precompute category output.

An independently discovered Python implementation, pymdb commit 04380153a98580b7097de30520ed5a05005aaf2d, independently confirms live catalogue membership, descriptor classes, raw lengths and rate pairs, master names/types/bins, and file-to-master links. All 2,156 file and 1,236 master full 32-byte identities match exactly. The remaining 359 file and 184 master legacy 12-byte identities match canonical material aliases. pymdb is useful structural corroboration; its UTF8 replacement decoding corrupts MacRoman text, so its convenience strings are not an oracle.

Two meaningful differences remain between Bella and current OldScanner:

1. Bella loses Kind for 30 JPED records.

All 30 occur in the installed SupportingFiles database. Bella retains descriptorClass=JPED and valid length/raster/codec/depth, but returns MdbKind::Unknown. OldScanner returns video. The fresh MDB itself declares the class chain JPED -> CDCI -> DIDD -> MDFL in CLSD objects 70579, 70578, 70577 and 70576. Media Composer's native JPED constructor and IsInstanceOf logic corroborate that image ancestry. Bella's classification whitelist at src/bella/mdbparser.cpp:1902-1905 omits JPED although pictureDescriptor() already recognizes it. This is a demonstrated under-classification, not missing evidence.

Use the existing descriptor classification helpers consistently as the immediate correction. MPGA, WAVE and TIFD are also recognized elsewhere but omitted by the Kind whitelist; no native TIFD/MPGA/WAVE descriptor case was present to quantify their effect. A carefully validated class-dictionary inheritance path would improve future private-subclass classification without assuming unknown descriptor payload semantics.

2. Bella correctly retains 86 direct file-owned project values that current OldScanner leaves blank.

The values are PeleSympProj (3), BLOCK_1729_PS_DG (34), and BLOCK_1730_PB_PA (49). All 86 have their own direct _PJ attribute. Each immediate upstream source records a different project; its linked master has no own project. Bella returns the file's own _PJ with OwnFile selection. Current OldScanner combines different owners' candidates and withholds a value because they conflict. Independent raw attribute/source/master traces are in online/project-validation.json. This is a concrete Bella accuracy benefit, not a guess that a nonempty value is preferable.

MDVx comparison

The installed MDVx is version 0.2 build 4073. Its original arm64 MDB methods were invoked through a fresh harness: a separate executable copy was converted to a loadable Mach-O bundle and ad hoc signed; the installed executable was untouched. Input loading uses NSData read-only access. This tests original MDB code, not a reimplementation, but it is not a full PMR-assisted GUI scan.

MDVx opens all seven Avid inputs and rejects all six unrelated LMDB inputs. Its native live composition counts total 1,420. All 2,515 file and 1,420 master identities join uniquely against its live HEAD-selected objects. All master names agree. All 1,002 comparable stored video FourCC/resolution-ID values agree. All 1,511 comparable PCMA audio frequencies agree. Available raw component widths/sample bits agree; raw width sentinels must not be compared directly to Bella's interpreted bit precision.

MDVx is less accurate for project text on this corpus. It returns zTe§t where the original MacRoman byte 0xA7 means zTeßt: 361 project values are affected (359 Shared MXF files and two Shared OMFI files). MDVx returns no project for another 108 files where Bella supplies one. The remaining 2,046 projects agree. These are original native getter results; no formatting-only dictionary/list mismatch is counted as a decoding error.

The native MDB summary interface does not provide an independent duration, raster or audio/video Kind oracle. MDVx also synthesizes _AUD and zero/default struct members in some cases; these are not recorded codec properties. Its manual's captured/imported/precompute Kind is a different concept from Bella's audio/video Kind. Never copy native output indiscriminately into the parser.

Binary reverse engineering

Genuine Hopper pseudocode exports were captured for 12 targeted MDVx MDB routines and 10 selected Media Composer routines, with supporting arm64 disassembly. This is targeted MDB reverse engineering, not a claim that both applications were completely decompiled. Some large functions have incomplete or register-level pseudocode; saved assembly is the reference in those cases.

MDVx exports cover opening, TOC1/TOC2, data bounds, text, project traversal, UID handling, compression and item enrichment. Its TOC2 route is a stub, so MDVx does not establish broad Bento2 support. Its compact identity comparison is not a reason to shorten Bella's full identity keys. A real file/master pair in EDIT/8646 shares eight material bytes while its complete IDs differ.

Media Composer is 26.8.0.58987. The inspected MDB-related implementation is principally libameLibrary.dylib, SHA256 659e3b6d07c9ae0d54f5741a153244e4a9c554d030c28e0cc7f4c73dba65ba22. Its CMGetProjectName at 0x282b9c uses _PJ before PROJNAME; JPED is in the digital-image class family; RationalFromExactEditRate at 0x258148 recognizes decimal aliases of 23.976 and 29.97 and produces 24000/1001 or 30000/1001 multiples for the internal ExactEditRate conversion.

That last rule is not proof that every arbitrary MDB rational must be rewritten. Preserve recorded numerator, denominator and type. Bella already preserves these and applies equivalent alias handling to numbering. Any duration/display adapter should carry the established ExactEditRate meaning forward instead of blindly treating every stored decimal as an ordinary rational. Media Composer's full Media Tool output was not used as a field-by-field runtime oracle.

Each ran all 13 fresh inputs: 637 historical process runs, all exit zero and no timeouts. The source-only historical selection, commit identifiers, build commands and raw outputs are retained. A source-deletion revision and a header-only declaration were excluded as non-implementations. Not every repository commit changing a transitive presentation helper was rebuilt.

The original parser history produces eight distinct normalized observed output groups. Implementations do not all return the same results.

The initial May heuristic emits 5,462 MobID-associated records without a comparable file/master split. It misses 184 active masters. Among 1,236 active matching IDs, 761 names and 602 bins differ from their active owning-object values. One actual clip Apple ProRes 422 HQ is assigned AVC Long GOP 35. Proximity-based string grouping should not return.

Previous Bella f287b1d and current 20220f2 return identical serialized reports on all 13 inputs after excluding elapsed time. The native corpus does not exercise every malformed/conflicting-data semantic difference between those revisions.

Performance and robustness

Five alternating-order Release runs per database used isolated processes and count-only output, with warm file caches. Bella's median parse/extract time was 2.0 to 9.75 times faster than current OldScanner's read/project path. On EDIT/86452, Bella measured 103 ms and 113 MB peak RSS; OldScanner measured 869 ms and 978 MB. These compare the actual current API contracts: OldScanner retains a much richer raw observation graph. They are not a claim about identical-functionality implementations or full-application scan speed.

AddressSanitizer and UndefinedBehaviorSanitizer ran both current parsers against all 13 original inputs plus 136 new deterministic truncation/TOC/bit-mutation cases: 298 process runs with no sanitizer reports, crashes or timeouts. These fresh mutation cases were generated solely for this audit; passing them is bounded evidence, not proof of universal memory safety or semantic validity.

What to improve

Priority 1: Fix JPED Kind classification and align the existing audio/picture helpers with descriptorFacts. Preserve the demonstrated active ObjectSpine ownership, complete identities, own-project precedence, typed rate values and qualified missing/unknown distinctions.

Priority 2: Restore useful MDB-only facts without restoring the old observation graph's allocation cost. Current OldScanner supplies channels on 1,513 records, source paths on 411, source-container values on 581, and imported status on 2,381; Bella's public report has no corresponding fields. These are source metadata, not guarantees about current physical paths or online status. Use precise ownership and evidence checks when adding them.

Priority 3: Bring over bounded cancellation polling. Bella checks whole-file/major-stage boundaries around readAll, establish and extract; OldScanner polls inside its 64 KB read loop and TOC iteration. A cancelled large database should not require an entire long parsing stage to finish. This is a source-level responsiveness weakness, not a crash observed in this corpus.

Priority 4: Add compact machine-readable field failure/ownership provenance where useful. OldScanner retains property names, object IDs, raw bytes and locations, while Bella's owned values mostly retain errors as free-text notes. Keep enough provenance for disagreements and unreadable/conflicting fields without copying every property into an expensive generic graph.

Priority 5: Treat broader Bento2/OMF2 support as a separate compatibility decision. Current OldScanner implements those paths; Bella explicitly supports the legacy Bento1/OMF1 MDB layout. All seven native databases here use that legacy layout, and MDVx's TOC2 stub does not supply an oracle for extending support. Obtain fresh genuine examples before expanding the parser.

Evidence and reproduction

The adjacent evidence directory contains compact primary findings, current comparison/benchmark/sanitizer receipts, corpus inventory, source hashes and decompiled MDB routines. evidence.tar.gz contains all fresh raw results, historical source snapshots and build adapters, newly retrieved publications, query logs, disassembly and reproduction scripts. Build outputs and modified executable copies are omitted; original installed executable paths and hashes are retained. The original native MDB files remain at their inventoried paths.

The verdict is specific: Bella is the preferred core for these databases, with one demonstrated classification fix and meaningful coverage improvements to make. Current OldScanner is equally accurate on live membership and many shared values; older versions and MDVx have demonstrated inaccuracies. No finite corpus establishes an objectively superior parser for every possible MDB.
