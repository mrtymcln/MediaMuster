# App update distribution

Distribution design, updated **2026-11-19**.

## Recommendation and machine reset timing

MediaMuster will retain macOS 11 support with Sparkle 2.9.6. On Windows, the proposed distribution is an MSI with in-app updates and a portable ZIP with download notifications. Both can use static HTTPS feeds hosted on Cloudflare R2.

A clean development-machine installation can happen **before generating new updater signing keys**, after exporting existing signing material and proving the current application can be rebuilt elsewhere. The wipe itself does not improve the update protocol. The reason to do it first is to establish a reproducible toolchain and avoid generating a new long-lived secret immediately before erasing its default storage. This ordering is a recommendation, not a framework requirement.

Before erasing the machine:

1. Preserve the repository, all uncommitted/untracked work, local configuration, and reproducible build instructions. The working tree contained unrelated source edits during this research; this note leaves them untouched.
2. Export the existing **Developer ID Application signing identity including its private key** as a password-protected `.p12`; keep its password separately. Apple's current path is Xcode Settings → Accounts → team → Manage Certificates → Control-click the identity → Export Certificate. A downloaded certificate without the private key cannot sign code. Import the identity on the replacement installation by opening its `.p12`. [Apple signing-identity export and recovery](https://developer.apple.com/documentation/xcode/sharing-your-teams-signing-certificates)
3. Preserve notarization credentials and access to Apple, GitHub, and Cloudflare. Record the existing CI secret names and keep recoverable originals in the project's secure secret store. Do not assume a local Keychain entry survives an erase: Apple explicitly recommends backing up signing assets, and downloading provisioning profiles does not restore private keys. [Apple signing-asset backups](https://help.apple.com/xcode/mac/current/en.lproj/dev8a2822e0b.html)
4. Verify a clean checkout builds and tests in CI; preferably validate signing with the exported identity in a separate temporary keychain or another Mac before wiping. After reinstalling, restore the same identity, build the current app, and complete a signed/notarized packaging run. Only then add updater integration and generate any new keys.

## Repository baseline

The inspected [CMake configuration](../../CMakeLists.txt) pins C++17 and Qt 6.5.3, already enables Objective-C++ on Apple platforms, and defaults to a universal arm64/x86_64 build with macOS **11.0** as its minimum. This is a Qt Widgets application, so Swift is not required for Sparkle integration.

The existing [macOS packaging script](../../.github/cmake/package-macos.cmake) runs `macdeployqt`, signs frameworks/plugins and the app, creates/signs a DMG, submits it for notarization, then staples and validates the DMG. The [Windows packaging script](../../.github/cmake/package-windows.cmake) produces a deployed directory; the [release workflow](../../.github/workflows/build.yml) zips it. It does not currently build a Windows installer. The workflow already imports a macOS identity from `MAC_CERTS_BASE64` with `MAC_CERTS_PASSWORD` and uses `APPLE_TEAM_ID`, `APPLE_ID_USERNAME`, and `APPLE_ID_PASSWORD` for notarization. Existing CI secrets do not replace an independently recoverable backup.

## macOS: Sparkle 2

Use exactly **Sparkle 2.9.6** for the integration. It is the latest published release that runs on Big Sur. The Sparkle project lists macOS 10.13 as the runtime minimum for 2.9.6 and raised it to 12 in 2.10. Keep MediaMuster's minimum at 11.0, review any future compatible fixes explicitly, and include a signed update on Big Sur in release testing. [Sparkle runtime requirements](https://github.com/sparkle-project/Sparkle#requirements), [2.9.6 release](https://github.com/sparkle-project/Sparkle/releases/tag/2.9.6), [2.10 compatibility change](https://sparkle-project.org/documentation/upgrading/)

Sparkle provides an official **Qt example and CMake guidance**. Keep a small platform wrapper: the macOS implementation is Objective-C++ with ARC, holds a `SPUStandardUpdaterController`, starts on the main thread, and connects the Qt update action to `checkForUpdates:`. Observe `canCheckForUpdates` to maintain the action's enabled state. Link and embed `Sparkle.framework` under `Contents/Frameworks`, preserve symlinks and executable modes, and configure its runtime search path. Add `SUFeedURL` and `SUPublicEDKey` through the existing Info.plist template. [Qt/programmatic integration and non-Xcode build details](https://sparkle-project.org/documentation/programmatic-setup/)

**The present signing loop needs extension.** Signing only the framework root does not re-sign its nested helpers. For this non-Xcode packaging workflow, Sparkle documents signing retained XPC services, `Autoupdate`, and `Updater.app` before the framework and outer app. Preserve the Downloader service's entitlements when applicable; do not solve nested signing by adding `--deep` to signing commands. `--deep` verification is a separate operation. Non-sandboxed applications may remove the unused XPC services following Sparkle's documented procedure, but the remaining helper tools still require correct signing. No sandboxing requirement is inferred for MediaMuster. [Sparkle manual signing and optional XPC removal](https://sparkle-project.org/documentation/sandboxing/)

Sparkle accepts DMG updates, so the existing distribution format is usable. Finish code signing, notarization, and stapling before creating the EdDSA signature for the exact archive bytes. `generate_appcast` can generate the RSS feed, archive signatures, and deltas from a directory of releases; configure the final download URLs and upload the referenced artifacts before publishing the feed. Retain a strictly increasing `CFBundleVersion`. [Sparkle distribution and appcast generation](https://sparkle-project.org/documentation/)

Sparkle's `generate_keys` stores the Ed25519 private key in the login Keychain and prints the public key. The documented backup/restore options are `generate_keys -x private-key-file` and `generate_keys -f private-key-file`. Encrypt exported backups and keep them outside the repository, app bundle, and public bucket. Export and test recovery immediately after generation. Changing the Developer ID identity and updater key together can break the documented rotation path; preserve continuity deliberately. [Sparkle key storage, export/import, and rotation](https://sparkle-project.org/documentation/)

Signed feeds are optional in modern Sparkle: `SURequireSignedFeed` requires `SUVerifyUpdateBeforeExtraction`, and modified feeds/release notes must be re-signed. If choosing these settings, treat key recovery and feed publication as explicit release requirements. With verification before extraction, EdDSA rotation has additional signed-DMG requirements. [Sparkle security settings](https://sparkle-project.org/documentation/customization/)

## Windows: WinSparkle

The official latest-stable endpoint resolved to **WinSparkle 0.9.4**. Current signing is **EdDSA using Ed25519**, available since 0.9.0; historical DSA instructions are deprecated. New integration should embed an EdDSA public key using `win_sparkle_set_eddsa_public_key()` or the `EdDSAPub` resource. The official migration guide says Sparkle and WinSparkle key files are compatible, though choosing separate platform keys is a reasonable isolation decision. [WinSparkle 0.9.4](https://github.com/vslavik/winsparkle/releases/tag/v0.9.4), [EdDSA migration](https://winsparkle.org/appendix/upgrading-from-dsa-to-eddsa-signatures/)

The native integration uses `winsparkle.h` and the appropriate `WinSparkle.dll`/import library. Set application metadata, feed URL, and public key before `win_sparkle_init()`; call `win_sparkle_cleanup()` at exit and `win_sparkle_check_update_with_ui()` for the menu action. Initialize once the main window is available. [C/C++ integration](https://winsparkle.org/guides/integrating-winsparkle/)

**Proposed Windows packages.** Compile MediaMuster once and package the same deployed Qt application as an MSI and a ZIP. Have the MSI install a package marker beside the executable. Use that local marker to select the installed feed, so a portable copy on the same workstation continues to use the portable feed. Give the two editions separate WinSparkle settings paths if their check preferences and skipped versions should be independent. Each release then needs an installed-upgrade test and a portable-download test.

- **MSI.** Users accept an update in the app. WinSparkle downloads and verifies the signed enclosure and starts Windows Installer. Author the MSI to upgrade the previous installation in the same scope. IT can deploy the same MSI to managed suites. [WinSparkle publishing](https://winsparkle.org/guides/publishing-updates/), [Windows Installer upgrades](https://learn.microsoft.com/en-us/windows/win32/msi/major-upgrades)
- **Portable ZIP with notifications.** Give its feed item a `sparkle:version` and an RSS `link` to the portable download page, and omit the enclosure. WinSparkle 0.9.4 displays **Get update** and opens the browser. The user downloads the ZIP, waits for current jobs to finish, closes the app, extracts the entire release into a fresh folder, and launches it. The browser handles the download, so WinSparkle's signature verification does not run on this ZIP. An existing release that predates update checking needs one manual download to acquire this feature. [WinSparkle appcast handling](https://github.com/vslavik/winsparkle/blob/v0.9.4/src/appcast.h#L102-L107), [button label and browser action](https://github.com/vslavik/winsparkle/blob/v0.9.4/src/ui.cpp#L676-L684)
- **Portable ZIP with automatic replacement.** A signed ZIP enclosure and a custom installer callback can hand the download to a separate helper. The helper must stage and validate the full app tree, wait for MediaMuster to exit, replace the executable, DLLs and plugins in a writable destination, recover from an interrupted replacement, and relaunch. Keep the user's media and operation journal outside the replacement. This option adds a second installation mechanism to maintain. [WinSparkle installer and shutdown callbacks](https://winsparkle.org/c-api/callbacks/)

Generate the key once with `winsparkle-tool generate-key --file private.key`. After the installer has its final bytes, run `winsparkle-tool sign -f private.key Updater.exe`, and attach the output as the appcast enclosure's `sparkle:edSignature`. Back up the private key securely; a lost key prevents issuing updates to clients trusting its public key. This updater signature is distinct from Windows executable/installer code signing. [Official signing commands](https://github.com/vslavik/winsparkle/blob/master/README.md?plain=1), [key backup requirement](https://winsparkle.org/guides/getting-started/)

## Hosting: Cloudflare R2

Use an application-owned HTTPS name, such as `updates.example.com`, connected to an R2 bucket as a **custom domain**. R2 buckets are private by default; connecting a public custom domain exposes their objects. The `r2.dev` development endpoint is rate-limited, intended for non-production use, and lacks the custom-domain caching/security features. Keep it disabled if unnecessary. The domain's zone must belong to the same Cloudflare account as the bucket. No Worker is required for simple public file delivery. [R2 public buckets and custom domains](https://developers.cloudflare.com/r2/buckets/public-buckets/)

Use the authenticated S3-compatible endpoint for CI uploads, with a token scoped to the release bucket. Keep upload credentials out of clients. R2 only displays the secret access key at creation, so store it safely or plan to replace the token. A production feed should reference stable public custom-domain URLs, rather than expiring S3 presigned URLs; those signatures work on the S3 API hostname and do not work on custom domains. [R2 authentication](https://developers.cloudflare.com/r2/api/tokens/), [presigned URL restrictions](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)

For the proposed Windows packages, use `macos/appcast.xml`, `windows/installed/appcast.xml`, and `windows/portable/appcast.xml`, with versioned immutable artifacts under `releases/<version>/`. Point the installed feed at the MSI and the portable feed at the ZIP download page. [WinSparkle feed publishing and compatibility](https://winsparkle.org/guides/publishing-updates/)

Use a long cache lifetime for immutable versioned artifacts. For changing appcasts, explicitly bypass edge caching and use `Cache-Control: no-store`, or choose a short documented TTL with a reliable purge process. Avoid a blanket cache rule that retains feeds. Cloudflare's default caching depends on extension, and edge caching can serve old R2 content after an overwrite despite R2's strong storage consistency. Publish artifacts and release notes first, verify their public bytes/signatures, then update the feed last. These cache settings and publication ordering are recommendations derived from the documented behavior. [Default cache behavior](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/), [R2 consistency and caching](https://developers.cloudflare.com/r2/reference/consistency/)

## Implementation and release order

1. Use Sparkle 2.9.6 for the macOS 11 target. Confirm which Windows packages will ship before wiring their feed URLs.
2. Create and immediately back up updater keys; prove restoration and signing in the intended CI environment. Embed only public keys. Keep Developer ID, updater signing, notarization, and R2 upload credentials as separate release inputs.
3. Add one Qt-facing update interface with Sparkle and WinSparkle implementations, user-triggered checks, and update preferences.
4. Integrate installation/relaunch with safe application shutdown. Defer it during copy, move, delete, rebalance, undo, recovery, scanning, and relevant modal decisions. Use [MainWindow::closeEvent](../../src/ui/main_window.cpp) and [FileOperationController activity/gates](../../src/ui/file_operation_controller.h) as integration points, consolidating the safety decision rather than assuming the current close handler already covers every operation. WinSparkle's can-shutdown and shutdown-request callbacks run off the app's main thread: marshal UI requests appropriately and use thread-safe state. [WinSparkle shutdown callbacks](https://winsparkle.org/c-api/callbacks/)
5. Extend packaging and CI to deploy updater dependencies, sign nested macOS code, produce the Windows update payload, create signatures/appcasts, and upload immutable artifacts before feeds. Keep publishing on the trusted release path.
6. Exercise a real old-version → new-version update on both systems through a test feed. Include invalid signatures, unavailable feeds, unsupported OS versions, blocked shutdown during an active job, and restart after installation. Validate with production-signed/notarized macOS builds because development signatures do not exercise every policy. [Sparkle production update testing](https://sparkle-project.org/documentation/)
